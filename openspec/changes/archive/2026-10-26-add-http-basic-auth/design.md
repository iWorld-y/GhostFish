# Design

## Context

需要认证的站点在 webview 里只会显示 401：系统 webview 不替应用弹登录框，而 mygo 上游也没有曝光认证质询。三个可选方向（凭据塞网址、本地反向代理、给框架补回调）都试过或评估过，实际采用的是第三条。

约束：应用仍然只在终端启动、无菜单栏图标、无前端页面；凭据不能进配置文件；探测量要小。

## Goals / Non-Goals

**Goals:**

- 需要 Basic 认证的站点能一次配置、长期免输地打开。
- 认证失败有确定的收手方式，不出现重试风暴。
- 无认证站点完全不受影响，包括不多一次可见延迟之外的任何行为。

**Non-Goals:**

- 不做 Digest、NTLM、客户端证书、OAuth/表单登录。
- 不做多主机凭据管理界面，凭据靠钥匙串按主机各存一份。
- 不改造 webview 的登录对话框外观。

## Decisions

**1. 走框架的认证质询回调，不在应用层绕。**
把凭据塞进网址（`user:pass@host`）实测可用，但密码会留在 URL、供页面脚本读取，也会进 shell 历史和进程列表；本地反向代理能藏住密码，却改变了源（origin），SPA 的绝对地址、CSP 与 cookie 作用域都会出问题。给 webview 补一个质询回调是唯一既保住源、又不暴露密码的做法，代价是要维护 fork。

**2. 探测和校验都用 GET。**
最初用 HEAD，遇到真实站点（luker）时服务器对 HEAD 或带 `Range` 的请求不认认证头，导致窗口还没开就判定"凭据错误"。改成和浏览器一样的 GET，读到 4 KB 就断开，代价是多一次很小的请求。探测时带上与 webview 一致的 UA，减少按 UA 拦截的误判。

**3. 校验是尽力而为，不是闸门。**
校验失败仍然把凭据交给窗口，因为探测请求和真实加载的差别可能来自服务器策略而非密码本身；只在终端说明状态码。真正的判定权留给页面加载。

**4. 密码只进系统钥匙串。**
钥匙串不可用时（用户拒绝授权、Linux 没有 Secret Service）认证仍可用，只是下次要再输。任何情况下不写状态文件，`state.json` 只放不透明度和穿透。

**5. 框架层在应用拒绝时取消质询。**
实测发现：应用给过一次凭据后，WebKit 把它缓存为会话凭据；之后应用返回空，默认处理会拿这份缓存凭据无限重发（错误密码那次 7 秒 7809 个请求）。所以框架在"应用有处理器但拒绝"时取消质询，只有"应用根本没有处理器"时才交回默认处理。应用层再叠一道上限：同一份凭据最多给两次。

## Risks / Trade-offs

- [fork 未合上游，换机器或升级 mygo 会丢回调] → `go.mod` 用 `replace` 指向本地 fork，README 写明 clone 路径；回调改动保持最小、可随时提 PR。
- [只覆盖 Basic，Digest/NTLM 仍打不开] → 绝大多数内部工具用 Basic；真遇到再按同样方式扩展到 Digest。
- [取消质询后页面表现为加载失败，用户可能以为是网络问题] → 终端提示"用户名或密码大概率不对"，并在提示里说明已停止重试。
- [钥匙串在首次写入时会弹系统授权] → 只在成功校验后写入，避免每次启动都弹。
- [探测多一次请求，可能触发站点限流] → 每次启动一次、读 4 KB 即断，且因为凭据会被记住，实际只在冷启动时发生。

## Migration Plan

无迁移：新能力，未认证站点行为不变。follower 需要在 `~/project/mygo` 放好 fork，`go.mod` 里那行 `replace` 已指向该路径。

## Open Questions

- Digest 是否值得补，等真撞上需要它的站点再定。
- 凭据过期后是否要自动重新询问：目前靠启动时的探测校验，过期会在终端提示但不会自动重问。
